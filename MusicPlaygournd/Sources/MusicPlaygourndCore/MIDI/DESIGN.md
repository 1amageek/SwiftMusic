# MIDI

## Purpose and Scope
Native macOS CoreMIDI input, output and transport-clock component. Parent: [MusicPlaygourndCore](../DESIGN.md). It has no children. Device selection and MIDI Learn UI belong to P07.

## Responsibilities and Boundaries
This component owns CoreMIDI clients, ports, endpoint identity, MIDI 1.0 UMP conversion, timestamped bounded ingress, scheduled egress, endpoint notifications and clock sequencing. [Playback](../Playback/DESIGN.md) owns the audible musical clock. [Rendering](../Rendering/DESIGN.md) owns loop events. MIDI neither edits/evaluates Swift nor owns/adopts PCM.

## Architecture
```text
CoreMIDI high-priority receive block -> Mutex<Ring[2048]> -> actor drain -> AsyncStream
PlaybackClockAnchor + PreparedLoop events -> bounded scheduler -> MIDIEventList -> endpoint
process-lifetime bootstrap MIDI client -> repeatable service-client create/dispose
CoreMIDI notifications -> actor endpoint registry -> route reconnect or typed disconnected state
```

## Contracts and Invariants
`MIDIEndpointID` wraps the endpoint's nonzero `MIDIUniqueID`. `MIDIEndpointDescriptor` contains `id`, `displayName`, `direction` (`input` or `output`) and `isVirtual`. Enumeration is stable by unique ID then display name; duplicate/zero IDs fail rather than alias routes.

`MIDIMessage` is `.noteOn(channel:note:velocity:)`, `.noteOff(channel:note:velocity:)`, `.controlChange(channel:controller:value:)`, `.clock`, `.start`, `.continue` or `.stop`. Channels are 1...16 and all seven-bit values are 0...127; note-on velocity zero normalizes to note-off. CoreMIDI endpoints are opened with `MIDIProtocolID.midi1_0`, so the system converts compatible endpoints to UMP. Unsupported UMP groups/status/data and SysEx produce a typed unsupported-message diagnostic; they never become another message.

`TimestampedMIDIEvent` contains source ID, CoreMIDI host timestamp, decoded message and optional `musicalBeat`. `MIDIScheduledMessage` contains a host timestamp and message. `MIDIReceivedClockState` contains configured source ID, running state, last Start/Continue/Stop command plus monotonic command generation, pulse ordinal, exact `pulseOrdinal / 24` beat and optional estimated BPM. `MIDIServiceSnapshot` contains connected input IDs, optional note-output ID, clock mode/health, optional received-clock state and monotonic dropped-event count. `MIDIServiceProtocol: Sendable` exposes async endpoint enumeration, `connectInput(_:)`, `disconnectInput(_:)`, independent `setOutput(_ id: MIDIEndpointID?)`, one `eventStream() async throws -> AsyncStream<TimestampedMIDIEvent>`, `updateClockAnchor(_ anchor: PlaybackClockAnchor?)`, `setClockMode(_:)`, bounded `send(_:to:)`, note `schedule(loop:from:through:channel:)`, clock-only `scheduleClock(from:through:)`, `snapshot()`, and `shutdown()`. A nil anchor marks normal waiting and schedules nothing; it is not an I/O failure. `CoreMIDIService` is the native actor implementation. A stream is single-owner; a second request fails typed. Shutdown is idempotent and finishes its stream.

An input route maps host time with the latest valid Playback anchor: `anchor.accumulatedBeatPosition + hostDeltaSeconds * anchor.beatsPerMinute / 60`. A stopped or unavailable anchor yields nil musicalBeat while preserving the timestamped MIDI event. Negative/nonfinite conversion and a host-time discontinuity are typed clock failures, not clamped beats.

A send call accepts at most 256 nondecreasing messages no more than one second ahead of the supplied anchor and encodes one bounded `MIDIEventList`; invalid ordering, range, endpoint or CoreMIDI status fails before partial success. Note output is independent of clock mode and uses the endpoint selected by `setOutput`; `.off` disables clock messages without clearing that note route. `.send(output:)` selects the same endpoint for clock and note output, while `.receive(input:)` leaves the independent output unchanged. Loop-note output schedules note-on/off only from `LoopEvent.midiProjection == .note`, plus event onset, velocity and audible duration, folds wrap exactly as the renderer does, and uses an explicitly configured channel. `.none` emits no note. Any `.unsupported` event in the requested scheduling horizon fails the entire batch with its typed limitation before CoreMIDI sees a partial sequence. MIDI never uses the display-oriented `midiNote` field or reconstructs pitch automation, envelopes, portamento, transpose or harmony.

Scheduling windows are unwrapped half-open beat ranges `[from, through)` with at most 100 milliseconds of host-time lookahead; SessionModel refreshes them every 50 milliseconds. `schedule(loop:...)` owns only loop-note edges and may run while clock mode is off; `scheduleClock(from:through:)` owns only 24-PPQN transport ticks and requires `.send`. Thus clock-only output never needs a fake PreparedLoop, and `updateClockAnchor` performs no hidden horizon scheduling. The service cursor keys note edges by loop occurrence and event index and clock pulses by absolute ordinal. It clips an overlapping retry to its unscheduled suffix, so polling, tempo-anchor refresh, code revision and override generation cannot emit the same edge or pulse twice. A new loop/generation begins only after the already-scheduled beat cursor; any prior message within the bounded lookahead remains immutable CoreMIDI output.

Every successfully sent note-on also commits one pending note-off record containing its original occurrence identity, channel, projected note and absolute unwrapped end beat. That record survives loop revision, override generation and tempo-anchor changes; its off edge is scheduled from the current clock mapping when the original deadline enters a later window, never re-derived from the replacement loop. Candidate cursor and pending-off changes commit only after the complete synchronous CoreMIDI batch succeeds. At most 2,048 sent occurrences may await note-off across the service; a candidate exceeding that bound fails `tooManyActiveNotes(limit: 2_048)` before sending any new note-on. A stopped anchor calls `MIDIFlushOutput` for the owned destination, immediately sends note-off for every service-tracked occurrence plus Stop when clock-send was running, and clears pending note edges while retaining the stopped transport position and clock ordinal. The first send-play in a service lifetime, or a play after `restartFromBeginning()` rewinds the anchor to beat zero, emits Start and resets its send ordinal. A same-service `play()` resuming a nonzero stopped beat emits Continue and resumes the ordinal aligned to that beat; no separate continuation configuration API exists.

`MIDIClockMode` is `.off`, `.send(output:)` or `.receive(input:)`; only one clock owner is active. Send uses the Start/Continue rule above, emits Stop on stop, and emits exactly 24 clock pulses per quarter note from unwrapped beat ordinals. Rolling scheduling never repeats an ordinal after an anchor refresh. Receive counts only the configured source's Start/Continue/Stop/Clock messages, resets pulse ordinal on Start, preserves it on Continue, and derives tempo from the median of the latest 24 positive pulse intervals. Until 24 intervals exist it reports waiting without changing playback rate. An out-of-range derived rate is a typed clock failure and retains the last valid audio/rate. SessionModel applies each new command generation and valid tempo through MainActor Playback APIs; MIDI callbacks never call the engine or derive a second audio clock.

## Runtime Flows
```text
input callback -> validate/decode -> bounded ring -> actor -> anchor mapping -> event stream
engine anchor -> note/clock ordinal selection -> host-time encode -> output endpoint
notification -> rebuild registry -> reconnect same unique ID | disconnected diagnostic
```

## State, Ownership, and Lifecycle
An internal process-lifetime CoreMIDI runtime owner creates one bootstrap `MIDIClientRef` on MainActor before the first service client and never explicitly disposes it; CoreMIDI reclaims it when the process exits. Bootstrap creation failure is the original typed `OSStatus` construction failure and no service client is created. This client owns no ports, endpoints, routes or callbacks with application behavior. Its sole invariant is that disposing a service client cannot dispose the process's last CoreMIDI client and stop the server, so repeated public `CoreMIDIService` init/shutdown remains valid in one process.

Each `CoreMIDIService` separately owns its service client, input/output ports, endpoint registry, routes, stream continuation, ring and clock ordinals. Native construction is MainActor-isolated so bootstrap admission, service-client creation and notification registration occur on the macOS application's serviced main run loop; the actor remains the owner of later serialized state and I/O. The receive block captures only the ring owner. The actor performs stream yields, CoreMIDI sends and external coordination outside the ring lock. Removal marks a route disconnected and stops scheduling; reappearance of the same unique ID reconnects once without duplicating a port connection. Shutdown disconnects sources, disposes every port/endpoint and the client owned by that service, finishes its stream and prevents later callbacks/yields/sends; it does not dispose the process bootstrap. Production uses the existing `NSApplication` main run loop and does not add periodic endpoint enumeration or a dedicated notification thread. Consuming the callback's bounded notification flag during the service's existing actor drain cadence is notification delivery, not a polling scan.

## Failure, Concurrency, and Constraints
The receive ring stores 2,048 fixed-size decoded events and discards the oldest on overflow so recent note-off/control state remains observable; `MIDIServiceSnapshot` reports a monotonic dropped-event count and route/clock health. The callback performs checked parsing and a short Mutex write only: no allocation, await, I/O or external callback. Actor state serializes endpoint changes, sends and shutdown. Endpoint absence, OSStatus, malformed packet, overflow, unsupported message, stream reuse, clock discontinuity and post-shutdown calls have typed errors or snapshot health; current audio continues. If projection validation, a missed scheduling window, clock conversion or synchronous send makes note scheduling fail, the service first flushes its owned future output, sends immediate note-off for every tracked occurrence where the endpoint remains usable, and resets note/clock cursors before returning the original typed failure. Cleanup OSStatus failure does not replace that original error and remains visible in `MIDIServiceSnapshot.clockHealth`, so retained-note risk is never hidden.

## Verification and Change Impact
Swift Testing uses MainActor-created CoreMIDI virtual source/destination endpoints and the real MIDI 1.0 UMP APIs to prove enumeration, note/CC/realtime round trip with host timestamps, exact beat mapping, 2,048-entry ingress overflow accounting, ordered send validation, pending-off capacity, stream finish, idempotent shutdown and successful service creation after an earlier service has shut down. `MIDIServiceTests` and `MIDIClockCompositionTests` are members of the same process-wide `NativeHostTests` serialization boundary as every other native CoreMIDI/audio test; separate suite-level serialization is insufficient because disposing a CoreMIDI client changes process-global server lifetime. Because the SwiftPM async test executor does not service the process main run loop, endpoint removal/reappearance and reconnect run in a test-only native executable whose synchronous `@main` creates the service on the true main thread, starts bounded async assertions and runs `RunLoop.main`; the Swift Testing parent launches it with a timeout and checks its exit/evidence. This models the application's notification runtime without changing production scheduling. Playback tests inject render timestamps for anchor correctness. Composition proves a C4 event with integer +12 pattern transpose sends C5, fractional/time-varying pitch fails before output, a long note receives its original note-off after a loop revision/pitch generation change, loop note-on/off plus 24-PPQN Start/Continue/Stop crosses two wraps and a rate change, and malformed/disconnected MIDI preserves the adopted loop. Changes to host-time mapping reverify Playback; event timing or pitch capability changes reverify Rendering; route presentation waits for P07.
